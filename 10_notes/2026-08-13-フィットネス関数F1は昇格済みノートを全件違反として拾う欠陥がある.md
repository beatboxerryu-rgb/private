# 結論
フィットネス関数 F1（author=claude かつ status=verified は常に0件）は
機能しない。昇格したノートは author が claude のまま status が verified に
なるため、正常な昇格済みノートを全件違反として拾う。

# 昇格条件
F1 を Git ベースの検査に置き換え、実際に動作を確認できたら verified。

# 欠陥の内容
事実: 憲法2条は「Claude が作るノートの author は claude、status は draft」と定める
事実: 昇格はユーザーが status を verified に変更する操作であり、author は変更しない
判断: したがって昇格済みノートは必ず author=claude かつ status=verified になる
判断: F1 は「常に0件」を期待値としていたが、実際には「昇格が進むほど
      違反件数が増える」検査になっていた

# なぜ気づかなかったか
判断: F1 を設計した時点では昇格済みノートが0件だったため、
      期待値と実測が偶然一致していた
判断: 「誰が verified を付けたか」と「誰がノートを書いたか」を
      author という1つのプロパティで区別しようとしたことが原因

# 修正案（いずれも未実装）
判断: 案A Git の差分で検査する。Claude の書き込み後のコミットに
      status: verified への変更が含まれていれば違反。プロパティでは
      判別不能なため、履歴を見るしかない
判断: 案B promoted_by プロパティを新設し、昇格時にユーザーが記入する。
      ただしプロパティが増え、記入漏れがあれば検査が無意味になる
判断: 案C 昇格時に author を self に書き換える。書き換えの手間が増え、
      「誰が書いたか」の情報が失われる

判断: 案A を推す。ユーザーの作業が増えず、情報も失われない。
      ただし Claude Code 導入後（M3）でないと実行できない

# 影響
判断: M2 期間中は F1 が使えない。憲法2条を機械的に検査する手段がない
判断: 同期間は、Claude が verified を書いていないことを保証する仕組みが
      ユーザーの目視のみになる

# 反証
Obsidian のプロパティに更新者の情報が自動記録される仕組みがあれば、
案A 以外の選択肢が生まれる。未調査。
