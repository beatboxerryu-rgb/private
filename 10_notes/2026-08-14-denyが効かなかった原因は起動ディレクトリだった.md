# 結論
Claude Code の permissions.deny が機能した。原因は起動ディレクトリで、
ワークスペース外（C:\Windows\system32）から起動していたため
vault の .claude/settings.json が読み込まれていなかった。

# 昇格条件
1ヶ月運用して deny が回避された形跡がないことを確認できたら verified。

# 経緯
事実: 起動ディレクトリが system32 になっており、設定が読まれていなかった
事実: vault ディレクトリへ移動して起動し直したところ、/permissions に
      deny ルール6件が表示され、10_notes への書き込みが拒否された
      （出典: 本セットアップ作業での実機確認、2026-08-14）

# 有効な設定
deny のみを記述し allow は書かない。
Edit(./10_notes/**) / Edit(./50_laws/**) / Edit(./90_archive/**) /
Edit(./.obsidian/**) / Edit(./.git/**) / Read(./90_archive/**)

判断: Write ルールは公式ドキュメントに記載がないため使わない。
      Read と Edit のみで構成する

# Claude の誤り
判断: m3.md の導入手順に「vault ディレクトリへ移動して起動」と書きながら、
      実際にどこから起動されたかを確認しなかった
判断: 当初の settings.json に Write ルールと .claudeignore を含めていた。
      いずれも公式仕様の確認を怠った結果

# 残る限界
事実: Read と Edit の deny は組み込みツールと Claude Code が認識する
      ファイルコマンドに適用されるが、Python や Node のスクリプトが
      ファイルを直接開くような間接的なアクセスには適用されない
      https://code.claude.com/docs/ja/permissions (2026-08-13)
事実: Windows ネイティブ環境ではサンドボックスが非対応
      （出典: 本会話前半での調査、2026-08-07）
事実: ブリッジ経路は別枠で、承認後は 10_notes の内容まで読み取れる
      （出典: 庭師による実機確認、2026-08-14）

判断: 書き込みは技術的に止まったが、読み取りは止まっていない。
      Git の差分検知は引き続き必要

# 未検証
deny が実際に回避されるケースがあるか。1ヶ月の運用で観察する。
