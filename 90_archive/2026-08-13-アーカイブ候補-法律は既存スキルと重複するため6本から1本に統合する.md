# 結論
法律6本の起草を中止し、1本に統合する。既存の M365 スキル6本が既に法律として
機能しており、再定義は二重管理になるため。

# 昇格条件
M365案件を1件実施し、スキルと法律の役割分担が機能したら verified。

# 判明した事実
事実: 既存スキル6本は description に自然文の発動条件を持ち、本文に手順・観点・
      成果物形式を含み、前後関係がチェーン化されている
事実: 一次情報での裏取りと出典URL・参照日の記載が既に義務づけられている
事実: 各スキルは ID を採番する（GAP / FR / NFR / DS / TC）
事実: 設計スキルは Decision Log（採用案・不採用案・理由・トレードオフ）を
      残すよう求めているが、置き場を指定していない
      （出典: ユーザー環境のスキル定義を許可を得て確認。2026-08-13）

# 判断
判断: 法律として書こうとした内容の大半はスキルに既に存在する。劣化コピーになり、
      片方だけ更新されて食い違うリスクが高い
判断: スキルは description による自動選択が働くが、50_laws のノートは
      入口ノート経由の擬似実装。既存の方が確実
判断: スキルに無いのは vault との接続のみ。法律はそこだけを担う

# 最大の収穫
判断: 各スキルの ID が vault の検索キーになる。DS-003 の判断ノートが vault にあれば、
      次の案件で類似判断を引ける
判断: 「判断の記録を vault の中心に置く」という設計は、設計スキルの Decision Log 要求と
      一致していた。足りなかったのは永続化の置き場だけだった

# 役割分担
成果物（Word / Excel）= 何を作ったか。vault に置かない
vault のノート = なぜそれを選んだか。案件をまたいで一般化して残す
設計書内の Decision Log = 当該案件のもの。vault のノートとは粒度が違う

# Claude の誤り
判断: 資料と計画で「法律6本」を最大の残作業として繰り返し提示していた。
      スキルの中身を読まずに、名称から必要性を推測していた

# 未検証
1本に減らしたことで、カテゴリごとの差異を取りこぼしていないか。実案件で確認が必要。
